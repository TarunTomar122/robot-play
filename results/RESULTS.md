# Results

Generated by `scripts/analyze.py`. Intervals are cluster-bootstrap intervals that resample runs (a task and run seed share one memory), never single episodes. There is one confirmatory family per question: Q1 is notebook against starting fresh for each cheap model (2 tests, 97.5% intervals), Q3 is the four frontier-versus-cheap gaps (98.75% intervals), Q4 is the notebook-against-fresh drop in the no-catch control scenes for each cheap model (2 tests, 97.5% intervals). Everything else (Q2, replay, per-task rows, the catch-scene recovery, the pose-level runs) is exploratory and uses unadjusted 95% intervals (the project's interval rule, no multiplicity correction). Held-out episodes are the four evaluation layouts of each run, played with the memory frozen. 'Calls to success' charges a failed episode the whole call budget.

### 2a. A tool-state artefact in the Q1 cell, and how much it could matter

In the skills cells a model can still call `move_to` and `close_gripper` by hand. A `move_to` can also answer ok while stopping more than 1 cm from the request. Both come from the frozen simulator, which I will fix after the run (not mid-matrix). ## 4. Q3: can a cheap model with experience come close to a frontier model's first try?

Confirmatory for the notebook rows (4 gaps, 98.75% intervals). The frontier models ran at reasoning effort `low`, like every model here, so this compares models at the same low setting, not at their best. Clusters are (task, run seed) runs, because the four layouts of a run share one notebook; the interval is the wider of the cluster bootstrap and an Agresti-Caffo interval whose cheap-arm variance carries the design effect fixed in PROTOCOL.md (max(2, 1 + 3 x rho), rho measured on that cheap model's own notebook held-out outcomes; the frontier arm and the no-memory row have none). A cluster counts only when all four of its layouts are paired (a block that is only partly observed is left out and reported), so it does not shrink to zero when every episode succeeds. Fewer than 12 of 15 complete clusters is inconclusive. A frontier first try below 50% is not treated as a target. ## 9. Deviations from the protocol

**Deviation 1 (analysis rule, before any result was analysed).** At 21:10 on 16 Nov the matrix started with the pre-registered small-sample rule "multiply the half-widths by sqrt(k/(k-1))". Council round 4 (a simulation by the Fable judge) showed that this factor is 1.017 at 30 clusters and leaves the Q1 and Q4 intervals near 95.5% coverage for a nominal 97.5%. At about 21:19, before any matrix result had been analysed (only run counts had been looked at), the rule was replaced by a stricter one: every interval is the wider of the percentile bootstrap and a stratified t interval (PROTOCOL.md section 1). The Q3 intraclass correlation was also restricted to notebook runs to match the protocol text. No run, prompt or tool was affected.

**Deviation 2 (borrowed-notebook cell, exploratory).** While that cell was running from a separate checkout, an edit to that checkout (adding the code for its wrong-task control) changed the code hash of runs that started after the edit. The cell was stopped, the edit set aside, and the four run files that carried the new hash (each had at most a few finished episodes) were deleted and rerun. The killed workers of that first start also kept running for a minute and appended rows to files after the restart, so six more files (two with a missing header, four with duplicate rows) were deleted and rerun as well, and the borrowed cell was verified to have exactly 30 run files with 4 unique episodes each and one code hash. The few cents these discarded attempts cost remain in the spend ledger but not in any run file. Every borrowed run file therefore carried one code hash **when this was written; the addendum below corrects that**: the cell later finished with two hashes (run seeds 0 to 4 and 5 to 9). The `borrowed_other` control cell is run from the edited checkout after the first cell has finished, with its own hash.

**Deviation 3 (one layout the environment cannot place, found at 22:10).** The pose sampler cannot place the flasks for evaluation layout seed 20801 (run seed 8, second held-out layout), in both the catch and the control scene; a scan of every practice and evaluation seed of run seeds 0 to 19 in all three jobs found no other such layout. Every flasks run with run seed 8 therefore ends with a crash at that episode ("could not sample poses") and is never complete: the Fable notebook run for run seed 8 (so the borrowed and wrong-task cells have 14 of 15 notebooks for run seeds 5 to 9), and in the main and control cells the flasks runs of run seed 8 for both cheap models. They are listed as incomplete in the coverage table and excluded by the complete-runs rule, leaving 29 of 30 (task, run seed) pairs for flasks-affected comparisons, above the registered minimum of 24. The sampler was not changed because that would change the code hash in the middle of the matrix; run_night.sh will end with NIGHT_INCOMPLETE because of these crashes, which is expected.

**Deviation 2, addendum.** The borrowed cell has two code hashes: run seeds 0 to 4 ran under `1cd309b2c89e94d7` and run seeds 5 to 9 under `bdda918f09675319`; the second differs from the first only by the extra `borrowed_other` cell and its prompt label (112 of 112 tests pass on both, and the prompt a `borrowed` run sees is identical). Every `borrowed_other` file carries `bdda918f09675319`. Flasks run seed 8 crashes in `borrowed_other` as in every cell (deviation 3), and the matching cell has no run there because Fable's notebook for it does not exist; sort run seed 8 has no wrong-task run for the same reason.

**Deviation 1, addendum (22:24).** A third piece of the interval rule was added before any confirmatory analysis was run, but not before anything had been seen: the exploratory Q5 table read at about 21:57 already showed Haiku's no-memory and own-notebook success on run seeds 0 to 4, which is half of Haiku's Q1 data. A floor can only widen an interval, so it cannot make a result look better, but the claim "before any result was seen" would be wrong. Added: a binomial sampling-noise floor (PROTOCOL.md section 1), because an exploratory table (Q5) showed a zero-width interval where every run of a task had the same outcome, which the bootstrap and the t interval over run means cannot avoid. The same floor protects the Q1 and Q4 intervals.

**Deviation 2, addendum (22:54, from council round 5a).** (a) The ten run files deleted in that clean-up were deleted, not archived, so nobody can check that the deletion was blind to outcomes; only the spend ledger remembers them. They held at most a few finished episodes each, were identified by their code hash or by a missing header or a duplicate row (not by outcome), and from now on discarded files go to `runs/_archive`. (b) The `borrowed_other` registration was committed at 21:40, while the matching `borrowed` rerun was running (its first episode 21:37, its last 21:46). From my notes no borrowed result had been read by then: the first Q5 table was read at about 21:50, after that cell finished. That is my recollection of the log, not a recorded fact.

**Deviation 3, addendum (22:54).** The exclusion is decided by the layout seed alone, before any model call, in every cell and condition, so it cannot select on outcomes: a scan of all 1,920 planned practice and evaluation layouts of run seeds 0 to 19 in three jobs and both scenes, repeated independently by the Fable judge, finds only flasks seed 20801 unplaceable. It is also an engineering miss: a one-second scan of the planned seeds before launch would have found it and saved the Fable run that crashed at episode 13. After the matrix a test that every planned layout can be sampled is added. The flasks denominators are 29 (task, run seed) pairs for every flasks comparison and 30 for the other two jobs; the three playable layouts of run seed 8 were never played (the run stops at the crash), so no sensitivity row can include them.

**Deviation 4 (22:54): a tool-state artefact in the frozen simulator, found by the Fable judge in round 5a.** In the skills cells a model can still call `move_to` and `close_gripper` by hand. `close_gripper` attaches an object to the hand whenever both fingertips touch it, including when the fingertips rest on top of it, so it can answer `holding` with the hand nearly closed (under 3 cm); `pick` then says `already holding` and `place` says `not holding anything`, and a `move_to` can answer ok while stopping short. In the Haiku `stack` no-memory held-out episodes 9 of 40 (run seeds 0 to 9) and 13 of 40 (run seeds 10 to 19) contain such a false `holding` (8 and 9 of them failed), against none in the notebook and replay arms. The effect does not depend on it (28 of 40 fresh episodes never tried `grip_level firm` and 25 of those failed), but its size does: if every failed false-hold episode had succeeded the Haiku `stack` gap would be about +48 points instead of +68. The report counts these episodes per model, job, condition and phase and prints Q1 with those episodes dropped from every arm and counted as successes in every arm (section 2a of `results/RESULTS.md`). The code is frozen until the matrix ends; the fix (attach only when the finger width matches the object, and report a stop short) comes after it and is a different code hash, so it will be a labelled follow-up and not part of these numbers.

**Deviation 5 (17 Nov, 01:26 to 01:35): a merge briefly deleted the Panda model directory; 72 empty run files were moved aside.** When the five exploratory branches were merged into `main` after the matrix ended, the `q5-borrowed` branch turned out to carry a symlink named `third_party` (a self-referencing link I had created in a worktree and committed by accident). Git replaced the ignored `third_party/` checkout of the Panda model with it, so for about three minutes (01:26 to 01:29) every worker that started failed to find the model; the test suite also failed (63 of 130) until I removed the link and restored the model from another worktree at the same pinned revision (the asset hash `dc07ba44218e72a9` is identical to the one in the other worktrees, and all 130 tests pass again). **What it cost the data:** runs that started in those minutes crashed before playing an episode but had already written their header line, with a code hash computed over a missing model directory (`c3e93e48a41a5f32` in `runs/rep_fixed`, `1eb779dc895dd674` in `runs/prior`); the runner correctly refused to resume them (`config_mismatch`). All 72 such files held **zero episodes**; they are kept in `logs/quarantine_outage_0126/` (not in the repository) and those runs were redone from scratch. **A second group was kept:** 14 files (8 in `runs/rep_fixed`, 6 in `runs/prior`) carry a zero-cost abort record from the same minutes but had the right header, so the runner resumed them in place; in 11 of them nothing had been played yet and in three `prior` runs (a stateless arm, a fixed borrowed notebook) 1 or 2 episodes had been played before the crash and were kept. They carry the correct code hash, every later episode follows the plan in order (`scripts/check_run_files.py`), and the abort record is visible in the file. No episode from before or after the outage was changed, and a scan of every `runs/*` folder shows only the expected code hashes (table in `results/code_versions.md`). The stray symlink is removed on `main`; it is still in the history of the pushed `q5-borrowed` branch and the three `code-borrowed-*` tags.

**Deviation 6 (17 Nov, 02:10): orphaned workers wrote duplicate episodes into 8 replication files; those runs were redone.** When I restarted the corrected-simulator replication with more workers at 01:26 and 01:32, I stopped the runner process but not the worker processes it had spawned, so a few workers of the old pool kept finishing the runs they already held while the new runner started the same runs again. The result was **8 of the 120 replication run files** (all `none` arm, `bins`: Haiku run seeds 25 to 28, Luna run seeds 24 to 27) with repeated episodes of the same layouts (21 to 37 episodes in a 20-episode plan). The no-memory arm has no state shared across episodes, so no memory could have forked, but a repeated layout is counted twice. A check of every run file in every folder for repeated or out-of-order (phase, index) pairs found only these 8; the 8 files are kept in `logs/quarantine_duplicates/` (not in the repository) and those runs were played again from scratch with no other process running. The numbers in section 6c and everything compared with `rep_fixed` come from the rerun. Lesson: a runner must be stopped together with its workers (kill the process group, not the parent), and `scripts/check_run_files.py` (added with this note) checks every run file for repeated or out-of-order episodes; it reports all folders clean after the rerun.
