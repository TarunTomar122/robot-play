# robot-play protocol (overnight pilot, v1.3)

This document is written **before** the paid experiments run. It fixes what is compared, how many runs there are, what counts as success, which numbers
answer which question, and which results would count against each claim. Anything that deviates from it in the results is listed in `results/RESULTS.md`
under "Deviations". Section 10 lists every change made to the setup and why, including the ones made after looking at a few live model runs.

## 1. Questions, measures and what would count against each claim

Setting: a language model orchestrates a simulated Franka Panda through tools built on inverse kinematics and collision-checked motion planning. No weights
are trained. Each task has a physical **catch** (section 2). Between episodes the model may update a small memory (section 4).

A **run** is one model on one task with one memory condition and one run seed: 12 practice episodes with the memory carried over, then 4 **held-out**
evaluation episodes on layouts the practice never used, with the memory frozen. Every interval is a **cluster-bootstrap** interval (10,000 resamples) that resamples whole
runs (a task and run seed, because the episodes of a run share a memory), inside each task so every resample keeps the task mix. Never single episodes, never single layouts. **Small-sample rule (fixed here, strengthened on 16 Nov 21:19 after the matrix had started and before any matrix result was analysed, see section 10):** a percentile bootstrap from few clusters is too narrow, so every interval of a mean (and every difference of two means) is the **wider of the percentile bootstrap and a stratified t interval**, the estimate plus or minus t(1 - alpha/2, k - h) x s / sqrt(k), where k is the number of clusters (pairs), h the number of tasks (strata) and s the pooled within-task standard deviation of the cluster values; for a difference of two such means the variances add and the degrees of freedom are the smaller of the two. In a simulation of the Q1/Q4 design (3 tasks x 10 run seeds, nominal 97.5%) the bootstrap and t rule covered 98%. **A third piece, added at 22:24 on 16 Nov before any confirmatory result was analysed (an exploratory table had shown a zero-width interval where every run of a task behaved the same):** for Q1 and Q4 the interval is also never narrower than a **sampling-noise floor**, the estimate plus or minus z x sqrt(sum of p(1-p)/(n+2)) over every proportion in the difference (two for a notebook-minus-fresh success difference, four for a difference of drops), each p with one pseudo-success and one pseudo-failure (Agresti and Caffo) and n the held-out episodes behind it, treated as independent. It binds only where the first two collapse. In simulation the three pieces together covered 98 to 100% in most designs and **95.8%** (rho 0) or 96.8% (rho 0.3) in the worst one tried, a small true gap with a cheap model at 0.96 against a notebook at the ceiling, where the nominal 97.5% is **not** met (each figure has a Monte Carlo error of up to 2.5 points; my first ad-hoc simulation, which was not saved, said 94 to 95%, and the Fable judge's own simulation said 95.3% for a similar case). The checked-in simulation is `scripts/coverage_sim.py` with its output in `results/coverage_sim.md`, run on the real `paired_difference` with notebook-arm episodes correlated within a run (rho 0 and 0.3); the Luna rows are in exactly that near-ceiling regime and should be read with about 96% coverage in mind, not 97.5%.

**Confirmatory and exploratory.** There is exactly one confirmatory family per question, fixed here before any reported run, with Bonferroni-adjusted intervals inside the family. Everything else is exploratory, uses plain 95% intervals and is labelled as such in `results/RESULTS.md`.
**Only runs that finished their whole plan are analysed**, so a paired comparison never mixes a run that stopped early with one that did not; the report lists, per cell, runs started, runs complete and abandoned attempts. A confirmatory claim needs enough complete runs (Q1: 24 of 30 (task, run seed) pairs per model, Q3: 12 of 15 clusters, Q4: 24 of 30 pairs per model; the control cell has 10 run seeds); with fewer it is reported as **inconclusive**. The report also lists every planned cell that never started, so a missing run is visible, and it says plainly that analysing complete runs only can select on how a run ended (a model that makes the provider fail more often under one condition would drop out of that condition).

| ID | Question | Confirmatory test (family) | The claim is *not* supported if |
|---|---|---|---|
| Q1 | Does experience raise success on a task with a catch? | Held-out success within the 20-call budget, **notebook minus starting fresh**, one test per cheap model (2 tests, 97.5% intervals), paired by (task, run seed). Exploratory: replay minus none, per task, and the **difference in differences** (gain with the catch minus the same gain in the no-catch control scenes) | The interval includes 0. We say the gain is *because of the catch* only if the difference-in-differences interval also excludes 0 |
| Q2 | Does experience make it faster and cheaper? | Exploratory only. **Calls to success** (the calls an episode used if it succeeded, the full budget if it failed, so a failure is never hidden), memory minus none, paired by (task, run seed), plus the same difference in differences against the control scenes; share of episodes within k calls, simulated seconds, dollars per episode (evaluation only) and per success | The interval includes 0. Practice and notebook-writing costs are not in the per-episode dollars; Q3 counts them |
| Q3 | Can a cheap model with experience come within a stated margin of a frontier model's first try? | Gap = frontier first-try success minus cheap-with-**notebook** success on the same layouts, for each of the 4 (frontier, cheap) pairs (98.75% intervals). The layouts of a run share one notebook, so **clusters are (task, run seed)**, and the interval is the wider of the cluster bootstrap and an Agresti-Caffo interval whose variance carries a **design effect fixed here**: the cheap arm's design effect is max(2, 1 + 3 x rho), where rho is the one-way intraclass correlation of that cheap model's own **notebook** held-out outcomes (clusters of 4 layouts sharing one notebook, pooled inside each task; only there is a memory shared), and the frontier arm has no shared memory so its design effect is 1, as is the design effect of the exploratory no-memory cheap row (a bootstrap alone has zero width when every episode succeeds, and at ceiling rho cannot be estimated, which is why the floor of 2 is there). With 60 layouts per pair and a design effect of 2, 60 of 60 against 60 of 60 gives an upper end of +6.9 points and 60 against 59 gives +10.5, so the +10 margin can be met only when the cheap model with a notebook matches a near-perfect frontier first try on essentially every layout. That is a stated limitation of the design, kept because a looser rule would let correlated layouts pass as independent; most Q3 rows will therefore be reported as gaps with their intervals, not as matches Exploratory: the same gap for the cheap model with no memory | The upper end is not below **+10 percentage points**, or fewer than 12 of 15 clusters are complete, or the frontier's first try is below 50% (then it is not a target). We then report the gap and do not say "matches". Cost counts **every** paid call of the cheap model (12 practice episodes, notebook rewrites, evaluation, retried and abandoned attempts) next to the frontier's first try plus its own abandoned attempts, as a descriptive table, not a cost-matched claim. All models run at reasoning effort `low`, so this compares models at the same low setting, not at their best |
| Q4 | Does experience help recovery from a disturbance? | In the **no-catch control scenes**, each memory condition's own **drop** in success from clean to disturbed on the same layouts (all assigned disturbed episodes), notebook's drop minus fresh's drop, one test per cheap model (2 tests, 97.5% intervals). Exploratory: the same in the catch scenes, only layouts where the disturbance fired for both conditions, and the share of clean wins that survive the disturbance | The interval includes 0. Control scenes are primary because there both conditions solve the clean layouts about equally often, so a drop is not floored by a failure unrelated to the disturbance (in catch scenes a fresh agent that already fails clean cannot drop, which would make the notebook look worse). A difference of drops is an association, not proof that the notebook taught recovery: the notebook is written from clean practice, so it can only help through general habits |

Null results are reported. Every number in the README comes from `results/RESULTS.md`, which `python scripts/analyze.py` regenerates from the run files.

**Floors and ceilings, stated up front.** The scripted oracle needs 5 calls for `stack`, 9 for `bins` and 5 for `flasks`, so no memory can bring the call count below those floors. Success has no room to rise where a model already succeeds without memory. The no-memory pilot on the final code (section 10; 8 layouts per cell, `results/pilot_no_memory.md`) gave, for stack, bins and flasks: Haiku 4, 6 and 8 of 8; Luna 7, 7 and 8 of 8. The pilot before the last fixes gave Haiku 1, 8, 8 and Luna 7, 8, 7, so a cell of eight layouts moves by several episodes from one pilot to the next. Four of the six cheap-model cells are at 88% or above and **Q1 is therefore mostly a statement about the cells that have room, above all Haiku on `stack` (and Haiku on `bins`)**; in the other cells the same improvement can only show up as calls, seconds and cost (Q2). The two questions measure the same effect from two sides, not two independent effects. All cells stay in the matrix and are reported as they are.

## 2. Environments

- Robot: Franka Panda (MuJoCo Menagerie, pinned to commit `370c439`, see `scripts/fetch_models.sh`). The SO-101 is future work; it is not in this pilot.
- MuJoCo 4.0.1; Python dependencies pinned in `uv.lock`; the two SDKs are pinned in `pyproject.toml`. Physics timestep 2 ms.
- Three tasks, each with one catch that is **fixed across all seeds** (the layouts are resampled each episode, the catch is not):

| Task | Goal (decided only by the simulator, after the model says `done` or runs out of calls) | Catch | Control scene (no catch) |
|---|---|---|---|
| `stack` | Red, green, blue stacked in that order, each within 12 mm of the stack axis, and **still for 1 s** (no object drifting more than 5 mm during that second) | The green cube weighs 250 g (the others 50 g) and has lower friction (0.5 against 0.9). **Hidden**: weight and friction are never shown | Green cube 50 g, friction 0.9 |
| `bins` | Every cube inside the bin of its colour: inside the bin's footprint, above its floor, below the height of two stacked cubes, and still for 1 s | The bin walls are 12 cm tall. **Visible geometry**: the wall heights are in `observe`. What they imply (the hand cannot reach over them while holding a cube low) is never stated | 1.5 cm walls |
| `flasks` | Both flasks upright (under 10 degrees) within 3 cm of their rings, standing on the floor and still for 1 s | Each flask has a 10 cm wide, 7 cm tall base under a 4 cm wide neck. **Visible geometry**: the flask sizes are in `observe`. The open hand is 8 cm wide, so the fingers land on the base | Plain 5 cm cylinder of the same height |

- Only the `stack` catch is hidden. For `bins` and `flasks` a model could in principle work it out from the visible sizes; the catch there is that the *consequence* has to be discovered by trying. The README says so.
- The collision model used by the planner is **identical** in catch and control scenes: the tools never route around a catch for the model.
- Settings that fix a catch are allowed and are written down, not assumed away: `results/settings_audit.md` changes one tool setting at a time and reports, per task, which settings alone solve or break which task. A setting that happens to solve a catch is another way to succeed, not a bug.

## 3. Tools (what the model can do and see)

Two toolsets. **Skills** (the main one): `observe`, `pick(object, grasp_height, speed, grip_level, yaw_offset_deg, lift_height)`, `place(target, release_height, speed,
settle_time)`, `move_to(x, y, z, speed)`, `open_gripper`, `close_gripper(grip_level)`, `home`, `done`. **Pose** (an ablation): the same without `pick` and `place`, so the model builds
them from moves and the gripper; its call budget is three times larger.

- Tool behaviours that matter for fairness: after `pick` lifts, the hand holds still for 1 s before `holding` is reported, so an object that is slipping out of the fingers is not reported as held. `move_to` waits 0.3 s at the end so a hanging load stops swinging. In the pose toolset, `close_gripper` treats an object squeezed between both fingers as part of the hand (the planner carries it and does not count it as an obstacle to its own hand), exactly as `pick` does; `observe` then lists it as held. In both toolsets the held state is refreshed from the simulator (in `observe`, `close_gripper`, `move_to` and `place`), so an object that has slipped out of the fingers or fallen off during a move is no longer reported as held.
- Descriptions are neutral. They say what a setting is, never which value is good for which task, and never mention a catch (`tests/test_leakage.py` checks the prompts, tools, observations, failure messages and the memory prompts).
- Tools return **measured facts only**: finger width, how far the object rose, tilt, contacts, planner and IK failure reasons. They never state a cause.
- `observe` returns exact simulator poses (no perception noise in the pilot).
- **Call budget: 20 tool calls per episode in the skills toolset (60 in the pose toolset), including `observe`.** Rule: about twice the oracle's calls on the longest task (bins, 9, rounded up to 20). It was in the code from the first commit and was **not** changed after the pilot.
- **One tool call per turn.** Parallel tool calls are switched off for both providers, so every call sees the result of the one before it.
- A reply with no tool call is answered with one reminder, at most twice. Provider failures and cut-off replies are **not** recorded as failed episodes (the run stops, the abandoned attempt and its cost are written into the run file, and the episode is redone on resume from the memory it started with; a notebook rewrite that fails or is cut off counts the same way, so a run never carries on with a stale notebook). A refusal by the model's safety system is recorded as a failed episode and counted.
- Success is decided only by the simulator. The model's own claim is logged and the rate of "said done, simulator disagreed" is reported.

## 4. Memory conditions (all without training)

| Condition | After each practice episode the model gets | Cap |
|---|---|---|
| `none` | nothing carried over | none |
| `notebook` | its own notebook, rewritten by the same model from the simulator's verdict and a shortened transcript (replace, not append). The writer is told object positions change every attempt | 600 tokens (2,400 characters) |
| `replay` | the transcript of its most recent successful practice episode on this task, if any | 1,200 tokens (4,800 characters) |

Caps are enforced as character caps at 4 characters per token. Evaluation episodes never change the memory. The tokens added to each episode's prompt are logged.

## 5. Experiment matrix and budget

Layout seeds: practice `10,000 + 100 x run seed + i`, evaluation `20,000 + 100 x run seed + j`. They are disjoint (tested), shared by every model and memory condition (so comparisons are
paired on the same layouts), and above every seed the validation gates used. Seeds 50,000 and up and run seed 99 were used for smoke tests and the pilot and are **excluded from every reported result**.

| Cell | Models | Tasks | Conditions | Run seeds | Episodes |
|---|---|---|---|---|---|
| Main | Haiku 5.5, GPT-6 Luna | 3 | none, notebook, replay | 10 | 2 x 3 x 3 x 10 x 16 = 2,880 |
| Disturbed evaluation, catch scenes (Q4 exploratory) | same | 3 | none, notebook | 10 | the 4 evaluation layouts again with a disturbance (slip on layouts 1 and 3, nudge on 2 and 4): 2 x 3 x 2 x 10 x 4 = 480 |
| Control (no catch) | same | 3 | none, notebook | 10 | 2 x 3 x 2 x 10 x 16 = 1,920 |
| Disturbed evaluation, control scenes (**Q4 confirmatory**) | same | 3 | none, notebook | 10 | 2 x 3 x 2 x 10 x 4 = 480 (the flask scene uses the slip on all four layouts) |
| Frontier first try (Q3) | Fable 5.2, GPT-6 Astra | 3 | none | 20 layouts each (the evaluation layouts of run seeds 0 to 4, i.e. 15 (task, run seed) clusters per cheap model) | 2 x 3 x 20 = 120 |
| Frontier with experience | Fable 5.2 | 3 | notebook | 5 | 3 x 5 x 16 = 240 |
| Pose-level tools (**exploratory**) | Haiku 5.5, GPT-6 Luna | 3 | none, notebook | 3 | 2 x 3 x 2 x 3 x 16 = 576 |

Total 6,696 episodes (2,880 + 480 + 1,920 + 480 + 120 + 240 + 576); `tests/test_agent.py` asserts every cell's count, that no two runs write the same file, and that practice, evaluation, gate and pilot seeds never overlap.

- **The pose cell is exploratory and does not isolate the abstraction.** It has three times the call budget (60, not 20), and in the `flasks` scene the planner refuses to put the open hand on a flask below about 65% of its height with the message `arm/hand would touch flask_a`, so the flask catch there is partly a planner message and not only the physical effect (the validation gate says so, section 7 item 3b). Two further known limits, found by reading the pilot and probe transcripts: in the pose toolset `close_gripper` still says `holding` for a cube that the closed fingertips merely rest on, and a `move_to` onto an object that is not really held can return `ok: true` about 2 cm short of the target. Both are counted from the run logs before the pose rows are read. The comparison with the skills toolset uses only run seeds 0 to 2 of the skills cell, so both toolsets see the same layouts, and reports the interaction (notebook gain with pose tools minus notebook gain with skill tools) with its own interval; three runs per task is too few for a narrow interval and the report says so.
- Hard stops: Anthropic **$90** of a $100 budget, OpenAI **$45** of a $50 budget. If measured cost makes the matrix infeasible, cells are dropped in this order: pose, control seeds, replay, frontier with experience. Expected spend is about $50 to $60 in total, most of it the two Fable cells; the cap, not this estimate, decides.
- Pinned IDs: `claude-haiku-5-5`, `claude-fable-5-2`, `gpt-6-luna`, `gpt-6-astra`.
- Provider settings, identical in spirit for every model: Anthropic `effort: low`, adaptive thinking left at its default (no `thinking` field is sent), default sampling, no refusal fallback (a silent switch to another model would corrupt "which model did this"); OpenAI Responses API with `reasoning.effort: low`, default sampling. Maximum output per turn: 6,000 tokens including thinking. The two providers do not think in the same way; that difference is part of what the cheap-versus-frontier comparison measures and is stated in the results.
- Runs execute in parallel worker processes. Every run is a JSONL file whose first line records the full configuration (model, task, memory condition, seeds, call budget, the complete episode plan, a hash of every prompt and tool schema, and a **hash of the package source and the pinned model download**). **A file whose configuration differs, including the code, is never resumed.** A deliberate code change can be declared with `ROBOT_PLAY_ALLOW_CODE_CHANGE=1`; it is then written into the file (`code_history`) and listed under deviations. `analysis.py` and `render.py` are not part of the hash because they never change what a run does.

## 6. Spend meter (enforced in code, covered by tests)

What it is and what it is not: a cross-process cap on **estimated worst-case cost plus settled cost at assumed list prices**. It is not an audit against the providers' invoices; the hard stops leave $10 (Anthropic) and $5 (OpenAI) of headroom for that, and the morning report asks for a comparison with the two billing consoles.

1. Before every paid call the worst-case cost is **reserved** under a cross-process file lock, and a call that would pass the cap is refused before anything is sent. The worst case prices every estimated input token at the dearest input rate (the cache-write rate) and assumes the full 6,000 output tokens, which is about 10 to 20 times the real cost of a typical call. The first call of an episode estimates its input from the text at 3 characters per token; later calls use the provider's own token count of the conversation so far plus the new text, plus 10%. These are estimates, not bounds.
2. After the call the reservation is replaced by the real cost from the response's usage. A call whose real cost is higher than its reservation is an **overrun**, written to the ledger and summed. **If overruns reach $1 in total, that provider is treated as exhausted and its remaining runs are skipped**, so an estimate that is wrong stops the experiment instead of silently drifting.
3. Prices. Anthropic prices, including the cache-read multiple of each model (0.1 for Haiku, 0.05 for Sonnet, 0.025 for Fable 5.2) and the 1.25 cache-write multiple, were checked against Anthropic's own model documentation on 16 Nov 2026. OpenAI prices could not be checked against an official list from here, so the meter charges **twice** the assumed OpenAI price (the cap can only be reached early) and **the OpenAI dollar figures in the results are assumed list prices, not verified**; any cost comparison that involves GPT-6 inherits that caveat.
4. A failed call that may have been billed (timeout, server error) is charged at its full reservation. Only failures that happen before the provider processes anything (bad request, rate limit, bad key) are released free. Every attempt, retries included, is counted in the episode's cost, and the cost of an attempt that produced no episode is written into the run file.
5. The ledger is a JSONL file that survives restarts. `reconcile` recomputes the totals from the ledger alone and compares them with the running state. When one provider reaches its cap, only that provider's remaining runs are skipped.
6. The council's judge calls run on the user's subscriptions and are not part of these caps.

## 7. Validation gates (before any paid run, on the final setup)

All gates play through `Episode`, the same wrapper a model uses (same call budget, same defaults, same `done` rule).

1. **Oracle gate:** on 100 layouts per scene, the scripted oracle succeeds in at least 95% and the naive script (all defaults) in at most 30%. In the control scenes the naive script succeeds in at least 90%.
2. **Dose-response:** naive success against the catch parameter (cube mass, wall height, flask base height), 30 layouts per point, so a null learning curve can be told apart from a catch that does nothing.
3. **Settings audit:** the naive script changing one setting at a time (`results/settings_audit.md`).
3b. **Pose-level gate** (`results/gate_pose.md`): the same oracle and naive scripts built from `move_to`, `close_gripper` and `open_gripper` inside the 60-call budget, 100 layouts per row, with the same thresholds. The naive pose script grasps flasks at 70% of their height (the planner will not put the palm on a flask top below about 65%, and the catch only bites below about 80%); both scripts carry at slow speed because a swinging load can slip, which is not the catch under test.
4. **Disturbance gate** on layouts **not used for tuning**: the disturbance fires in at least 95% of episodes; a script that knows the catch but never reacts succeeds in at most 30% of the episodes where it fired; a script that re-tries succeeds in at least 80%. The nudge was tuned on layouts 2,000 to 2,029 (`results/disturbance_tuning_seeds_2000.md`); the reported gate uses layouts 3,000 and up, in the catch scenes (`results/disturbance.md`) and in the no-catch control scenes (`results/disturbance_control.md`), because the control scenes carry the confirmatory Q4 measure.
5. **Predicate tests:** positive and negative cases for each success predicate, including a cube resting on another cube inside a bin and a tower still moving during the one-second window.
6. **Leakage tests:** no catch value or hint appears in anything a model is shown, which of the catches are visible geometry is tested, and practice and evaluation layouts are disjoint.

## 8. Disturbances (Q4)

Applied by physics, not by editing state, in the catch scenes and in the no-catch control scenes (the control scenes carry the confirmatory Q4 measure): (a) *slip*: the gripper is commanded open for 0.15 s after the object has been lifted 3 cm; (b) *nudge*: a 0.3 s horizontal force of
1.1 times the object's weight, pointing within 45 degrees of the x axis (from the front or back, because a sideways shove is caught by the open fingers), applied the first time the open
hand descends next to an object that is not yet grasped. In the no-catch flask scene the nudge topples the plain cylinder and nothing can stand it up again (the retry script recovers 0 of 50, `results/disturbance_control.md`), so that scene uses the slip on all four disturbed layouts. Timing is fixed relative to events, the same for every condition. The disturbed evaluation episodes reuse the four held-out layouts of each run, so each
layout has a clean and a disturbed outcome. "Tool failure" and "instruction change" are text injections and are not in the pilot.

**What we claim is new is the combination, not any single axis:** (i) the same task played through a skill-level and a pose-level tool API, so the effect of the abstraction on learning from experience is measured, not assumed;
(ii) catches validated by oracle gates, dose-response sweeps, a settings audit and no-catch controls; (iii) learning curves over 12 practice episodes with frozen-memory held-out evaluation and cluster-bootstrap intervals;
(iv) disturbance recovery as a function of experience, with the clean-to-disturbed drop as the measure; (v) a cheap-versus-frontier comparison with a pre-stated equivalence margin and every paid call of the cheap model counted next to the frontier's; and (vi) every paid call, including failed retries and memory-writing calls, counted by an enforced spend cap.

## 10. Changelog and history (up to v1.3 everything happened before any reported run; the v1.4 and v1.5 addenda at the end were written while the matrix was running, each dated to the minute and written before the cell it registers)

**v1.1, 16 Nov 2026.** Built the environment and played each task by hand through the tool interface. `bottle` (top-heavy, pinch-height quirk) became `flasks` (wide base, neck grasp): with a top-down hand the palm sits 4 cm above the fingertips, so a low pinch on a tall object is impossible, and a top-heavy bottle did not flop because the finger pads resist twisting. The stack cube changed from 0.9 kg to 250 g (the firm squeeze holds about 300 g); the gripper force was scaled 5 times so `light`, `normal` and `firm` differ. Contact physics became stricter (elliptic friction cone, `impratio` 10, finger-pad twisting friction). The nudge force and direction were tuned on layouts 2,000 to 2,029. No model results were used.

**v1.2, 16 Nov 2026, after the first live runs and the first council review.** Here is exactly what the model and the council changed, in order:

1. *Live smoke tests* (three episodes on layouts 50,000 and up; Haiku on `stack`, Luna on `bins`). Haiku issued dependent calls blindly in one turn (a `place` together with the `pick` that had just failed), so parallel tool calls were switched off for both providers. This is a validity decision about the harness, not tuning on outcomes.
2. *No-memory pilot* (48 episodes: Haiku and Luna, 8 layouts per task, layouts 50,000 to 50,007, call budget 20). Results informed the council review and the discussion of floors and ceilings in section 1. They did **not** change the call budget (section 3).
3. *Memory smoke test* (112 episodes, run seed 99, old code). It confirmed the notebook and replay loops work end to end. It showed that notebooks recorded episode-specific positions, so the notebook writer is now told not to. These episodes are excluded from every reported result.
4. *Council review 1* (Fable and Codex) found real defects, all fixed before any reported run: (a) the `bins` instruction said "resting inside the bin" while the predicate demanded the bin floor, so a cube resting on the other cube in the bin was marked wrong (all 8 pilot episodes of one model failed this way); the predicate now matches the instruction; (b) after `open_gripper` inside a tall-walled bin the hand touched the wall and every later move failed ("stuck arm"); the planner can now lift the hand straight out of a contact it starts in, and may not touch anything new on the way; (c) the stack predicate checked positions only at the end of its settle second, so it now also requires no object to drift more than 5 mm during that second; (d) "decoy" settings were not all harmless (for example a 45 degree hand turn can build the tower with the default grip), so the wording was corrected and a settings audit was added; (e) the validation gates bypassed the call budget, so they now play through `Episode`; (f) provider errors were saved as failed episodes, resumes did not check the configuration, a rate limit stopped everything, and the spend cap did not bound later calls of a conversation or cache writes: all fixed (sections 3, 5, 6); (g) the disturbance gate reported the layouts it was tuned on, so it now uses fresh layouts.
5. *Scope*: the budget was far larger than needed (measured cost about $0.002 per Haiku episode), so seeds were doubled in the main cell, a pose-level ablation and 20 frontier layouts were added, and the efficiency measure (calls to success) was fixed before any reported run.
